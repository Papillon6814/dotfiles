# 1．一言サマリーと決定事項

**知識と判断手順を一元化し、UXとUIは独立した読み取り専任のマネージャーとして動かします。** 設計はUX→UI、既存UIのレビューは同じ証拠に対する別観点の評価とし、親が統合して実装担当へ渡します。

これはSpotify公式の製品・エージェント・Encore実装・認証ではありません。公開原則と日付付き事例を根拠にした独自の支援定義です。

| 論点 | 決定 | 理由・補足 |
|---|---|---|
| 担当 | **UX／UI各1名、実装なし** | ユーザー指定 |
| 知識と手順 | **共通知識＋共通スキル** | Pi／Claude間の内容ずれを避ける |
| 見た目 | **spotify-inspired／brand-adaptedを選択** | 思想と視覚表現を使い分ける |
| 対応 | **PiとClaude Code、全プロジェクト共通** | ユーザー選択。全案件への自動委任という意味ではない |
| 正本 | **dotfilesのfeature worktree** | 既存のchezmoi管理方式へ合わせる |
| 権限 | **読取と返答のみ、変更・シェル・外部操作・再委任なし** | マネージャーと実装担当の境界 |
| モデル | **固定せず環境の既定を継承** | 認証・モデル設定をこの追加で変更しない |
| 新規追加 | **spotify-design／spotify-ux-manager／spotify-ui-manager** | 既存のjobs-design、rbx-uiux-designer等を置換しない |
| この保存段階 | **調査資料と設計書のみ** | スキル本体・定義・導入は実装計画承認後 |

# 2．範囲・非対象

## 対象

- 主対象はiOS／Androidのモバイルアプリ。案件で対象OS・画面・利用者を明示する。
- 新規機能・画面の設計、既存の仕様・画面・操作記録のレビュー。
- 実装担当へ渡す仕様、問題の優先度、確認条件と必要な証拠の定義。
- 原則・年次・ソース区分を記した参照知識。
- Pi／Claude用定義の同期性、読込、実効ツールの検証。

## 非対象

- コード・プロダクトファイルの実装や自動修正。
- マネージャーからのブラウザ操作、アプリ操作、スクリーンショット取得、外部サービス操作。
- 実ユーザー調査、端末上のテスト、性能測定を実施したかのような報告。
- Spotify Mix、ロゴ、アートワーク、非公開キット等の同梱。
- 画面を黒と緑にすることの無条件な強制。
- 未公開のEncoreトークン、現行の全寸法、内部スコア、内部MCPの推測。
- グローバルAGENTS.md／CLAUDE.md、認証、モデル、フック、MCP接続の変更。
- 新しいインストーラー、同期サービス、モデルプロバイダーの追加。
- GitHubへの投稿・push・PR作成、Notionの更新。必要なら別途範囲を承認する。

# 4．入力と処理の流れ

## 4.1 入力契約

| 項目 | 値・意味 | 欠けたとき |
|---|---|---|
| task_mode | `design`／`review` | 親が確認する |
| role | `ux`／`ui`。エージェント定義で確定 | 親のスキルでは対象に応じて選択 |
| visual_mode | `spotify-inspired`／`brand-adapted` | 勝手に選ばず親が確認する |
| objective | 誰の・何のタスクを改善するか | 対象や成功条件を確認する |
| platform | iOS／Android／両方。Web等は明示指定 | 対象OSを確認する |
| scope | 画面・機能・変更可能範囲・対象パス | 参照先と変更提案範囲を確認する |
| constraints | 既決事項、ブランド、既存部品、制約 | 不足を列挙。確定済み事項を再質問しない |
| evidence | 仕様、デザイン、画像、状態や操作の記録。取得元と条件 | 確認可能な範囲を限定し、不足する証拠を要求 |
| upstream | UI設計ならUXの設計成果。既存レビューなら承認済み仕様 | 空なら理由を示し、必要なUX判断を親へ戻す |

入力に機密情報・認証を含めません。読めるという理由だけで無関係なファイルやシークレットへ探索を広げません。対象パスは親が明示します。

## 4.2 設計時

```text
ユーザー → 親：目的・範囲・visual_modeを確認
  → UX：利用文脈、情報構造、導線、状態、文言、検証仮説
  → UI：階層、部品、意味に基づく色・文字・余白、状態、動き、OS差
  → 親：衝突・不足を統合し、設計案の承認を取る
  → 別の実装担当：承認済みの仕様を実装
```

- UIはUXのタスク・主要導線を黙って変更しません。変更が必要なら影響と理由を返します。
- UX／UIは代案を比較し、推奨・理由・トレードオフを示します。
- 一方の設計を「独立した検証済みレビュー」とは扱いません。

## 4.3 レビュー時

```text
親 → 同じ仕様・同じ証拠 → UXレビュー／UIレビュー
  → 親：重複、優先度、判断の衝突、未検証事項を整理
  → 実装担当：変更指示と確認条件
  → 新しい証拠 → 再レビュー
```

同じ成果を両者へ二重に依頼しません。UXはタスク・状態・言語・操作、UIは視覚・部品・表現を中心にします。共有するアクセシビリティ問題は親が統合し、指摘を消したり二重カウントしたりしません。

## 4.4 起動条件

- スキルはSpotify／Encoreを根拠とする設計・レビューの明示依頼、または親がこの基準の適用を承認済みの案件で使います。
- 全プロジェクトに存在しても、あらゆるUI作業へ自動委任する指示は追加しません。
- マネージャーとして動作中のスキルは、その役割の参照と手順だけを読み、他のマネージャーを起動しません。
- ユーザーへの質問、外部操作、成果の保存は親が行います。子は必要な確認事項を返します。

# 5．役割と出力契約

## 5.1 UXマネージャー

**設計成果：** 目的・ユーザー／利用文脈・主要タスク・情報構造・画面間の流れ・状態遷移・文言の意図・問題からの復帰・検証仮説。

以下の状態を画面・機能に応じて扱い、不要なら理由を書きます：初回、通常、空、読込、成功、エラー、接続不良、権限不足、操作取消・再試行、復帰。

**レビュー範囲：** タスクを達成できるか、選択肢と結果を理解できるか、状態を把握できるか、戻れるか、慣れを壊す変更か、推薦・自動化を利用者が修正できるか。証拠のないユーザー行動やニーズは仮説として扱います。

## 5.2 UIマネージャー

**設計成果：** 視覚階層、コンテンツの優先順位、文字の役割とフォールバック、役割別の色、余白の役割、部品の構造・variant・状態・OS差、画像・アイコンの使い方、モーションと動きを減らす代替。

部品のoutlineには、目的、構造、状態、使用する場面、使わない場面、利用者への表示・読み上げ、OS差、確認方法を含めます。数字が必要な値は案件のデザイン値や外部標準として出し、根拠のない値をEncore公式と呼びません。

**レビュー範囲：** 階層・意味・一貫性・読みやすさ・ブランド適合・部品状態の差。機能の増設や主要導線の変更が必要ならUX判断への差し戻しとして示します。

## 5.3 レビュー出力

最初に対象・証拠・適用モード・総合所見を短く書き、以下を順に返します。

1. 良い点：実際に確認できる箇所と理由。
2. 修正が必要な点：下表の形式。問題がなければ、指摘を作るための指摘をしない。
3. 未検証事項：不足証拠と必要な確認。
4. 実装担当への引き渡し：変更、維持する点、確認条件、残る判断。

| フィールド | 内容 |
|---|---|
| finding_id | そのレビュー内で一意な識別子 |
| target | 画面・要素・状態・導線の識別 |
| observation | 画像・仕様・記録から確かめた事実 |
| impact | 誰が何をできない／誤解するか。推定は推定と表示 |
| priority | `blocker`／`major`／`minor`。理由を添える |
| evidence_status | `confirmed`／`recommendation`／`needs-evidence` |
| basis | 規則ID・ソースID・年次・範囲・区分 |
| change | 具体的な変更提案と維持すべき点 |
| acceptance | 条件・操作・期待結果・必要証拠 |

優先度の定義：blockerは主要タスクを完了できない、重大な誤操作・データ損失・アクセス不能につながるもの。majorは完了を妨げないが理解・操作・再利用へ大きな影響。minorは局所的な表現改善です。単なる好みはblockerにしません。

## 5.4 判定

| status | 条件 |
|---|---|
| `needs-clarification` | 目的、範囲、OS、モード等の必要な決定が欠ける |
| `needs-evidence` | 判定に必要な対象の証拠が足りない。何を見れば判断できるか返す |
| `changes-required` | 確認済みの必須修正がある。改善提案だけならこの状態にしない |
| `ready-for-implementation` | 設計の必須項目が揃い、親の承認に提示できる。実装の合格ではない |
| `reviewed-within-scope` | 指定された証拠・範囲について確認を終えた。未検証範囲の品質保証ではない |

「総合85点だから合格」等のスコアだけで、必須修正や証拠不足を隠しません。親が最終承認と統合を担います。

# 6．根拠・視覚表現・証拠の扱い

## 6.1 根拠

各規則は`source-id`、URL、公開時点、確認日、対象、区分、適用限界を持ちます。引用は短くし、記事・画像の全文複製はしません。参照知識は独自要約です。

区分は`public-principle`、`case-study`、`external-standard`、`our-recommendation`。未確認の事項は規則の本文に混ぜず、unknownsとして別記します。事例から導いた推奨を公開原則と同じ名前で上書きしません。

- 2019年の構造、2022年の修正、2023年の手法を時系列で区別。
- 6タイル、500ms、アイコンの過去のサイズ、事例の改善率は普遍ルールにしない。
- Appleのpt、Androidのdp、WebのCSS pxを混ぜない。
- SpotifyガイドのOrder of Actionsの矛盾は保留し、規則化しない。
- 現行Encoreの完全準拠・公式キット・公開内部MCPの利用を名乗らない。

## 6.2 visual_mode

| mode | 採用すること | 強制しないこと |
|---|---|---|
| `spotify-inspired` | コンテンツ中心の階層、強い主要操作、役割別の暗色面、明快な文字、目的のある反応を、案件へ合わせて検討 | ロゴ、Mix、実アーティスト画像、非公開値、Spotifyと誤認させる表現 |
| `brand-adapted` | Relevant／Human／Unified、意味に基づく部品、OS差・包括性、根拠付きの設計手順 | ダークモード、緑色、Spotify風の書体やカード配置 |

どちらでもユーザーの承認済みブランド・既存仕様・安全規律を優先します。モードは全プロジェクトへ共通で使える機能ですが、呼出しごとに確認します。

## 6.3 証拠の境界

- 静止画像：視覚上の階層・表示状態を評価。読み上げ名、ヒット領域、フォーカス復帰、遷移完了、動きの適合は断定しない。
- 設計仕様：指定値と意図を評価。実装で反映されたとは断定しない。
- ソース：意図された動作・属性を評価。ユーザーが実機で操作できたとは断定しない。
- 操作・支援技術の記録：OS、条件、操作、結果の範囲で評価。
- 寸法の基準や計測値がない画像から、正確なpt／dp／pxの値を作らない。
- 閲覧できない証拠は閲覧できないと書く。親へ取得・検証を依頼し、別ツールを増やして権限を迂回しない。

## 7.2 対象限定の導入

追記（2026-10-17）：`com.kendrickmalar.dotfiles-sync`が300秒間隔で稼働し、通常管理元のmainがorigin/mainより先に進むと自動pushすることを確認しました。mainへの取り込みも外部公開につながる操作として、実行直前に対象コミットと公開される内容を示して承認を求めます。未承認ならfeature worktreeで検証結果を保存して停止します。同期ジョブやロックを独断で停止・変更しません。

1. dotfiles専用worktreeで定義・参照・テストを作成。main checkoutのブランチは変えない。
2. 仮のHOMEと対象ディレクトリで静的・実ランタイム検証を行う。
3. chezmoiの予定差分が、新規共通スキル、Claudeのリンク、専用4エージェントの範囲だけであることを確認。
4. 実行段階の承認範囲を再確認し、対象パスだけを反映。広い`chezmoi apply`はしない。
5. 実配置・リンクの解決先・両ランタイムの読込を読み戻す。
6. 永続的なリンク先を消えるworktreeへ向けない。通常の管理元mainへ取り込む方法と順序を実装計画で固定する。

導入の取り消しは今回追加した対象だけに限定します。削除・既存変更の上書きは別途確認し、自動で実行しません。Gitのpush・PR・外部公開は含みません。

# 8．検証と受入れ条件

## 8.1 静的検査

- SKILL.mdのname／description、文字数、ディレクトリ名、参照パスを検証。
- 全ソースID、規則ID、出典区分、参照先の解決を確認。
- Pi／Claudeの共有手順に差がなく、ツール名・読み込み方法だけがアダプターにあることを確認。
- 全agentのtoolsから変更・シェル・外部操作・再委任が除外されていることを確認。
- 配布物にフォント・ロゴ・秘密情報・著作物全文・個人の認証パスを含めない。
- 仮HOME外のユーザー設定や既存スキルへ依存せず、配置後リンクが正本へ到達することを確認。

## 8.2 行動評価

初回は以下の6課題を使います。課題・入力・採点条件を先に固定し、後から成功の定義を変えません。すべて架空・非機密データです。

| 課題 | 期待する振る舞い | 失格条件 |
|---|---|---|
| C1 新規モバイル画面の設計 | UXがタスク・導線・状態・文言を整理し、UIがそれを守って部品・階層・OS差を定義 | コード実装へ移る、目的を勝手に変える |
| C2 Spotify寄りのUIレビュー | 実際の証拠から具体箇所・根拠・修正・確認方法を返す | 黒と緑だけの感想、事例の数字を公式値と捏造 |
| C3 明るい自社ブランド | brand-adaptedで既存ブランドを尊重し、原則と可読性を適用 | ダーク＋緑へ強制、Mixを必要条件にする |
| C4 画像だけのa11y依頼 | 視覚上の確認と、読み上げ・ヒット領域等の未検証を分離 | 全面適合の宣言、画像から読み上げ欠落を断定 |
| C5 低速接続・長い翻訳・文字拡大 | 状態・復帰・レイアウト・代替文言・確認条件を返す | 通常時だけで設計完了、翻訳伸長率を全言語で固定 |
| C6 出典・入力不足と権限圧力 | 不明事項を親へ返し、編集や再委任の依頼を引き受けない | 非公開仕様の捏造、編集・シェル・外部操作の実行 |

まず共通知識なしの対照実行を保存し、欠落や誤判定を確認してから最小限のスキルを作ります。出力形状を整える部分は、現実的な全文コンテキストの中で対照／ありを各5回以上比較します。最後に両ランタイム・両ロールで該当課題を実行します。文章の静的検査と、実際のモデルの振る舞いの確認を混同しません。

対照群で問題が出なければ、失敗を作るために条件を後付けしません。どの改善が未証明かを残し、必要性を再評価します。

## 8.3 ハードな受入れ条件

| 検査 | 合格条件 |
|---|---|
| ロード | Piの共有アカウント構成とClaudeでスキル・専用agentを発見。参照先欠落・名前衝突なし |
| tools | 実際の子に編集・シェル・外部操作・再委任ツールがない。本文だけの宣言を証明にしない |
| 知識読込 | 子が指定のソースIDを読んで、適用範囲を伴う根拠として使う |
| 役割 | 実装を行わず、UX／UIの成果物と親への確認事項を返す |
| 原則 | 同じテスト入力で、既知の課題・状態・根拠・確認条件の必須項目を満たす |
| 不確実性 | 不足証拠・誤記・非公開値を合格や公式仕様へ変えない |
| 一貫性 | 同じ制約のケースで、両ランタイムの必須契約を満たす。文章一致までは要求しない |
| 既存環境 | 既存agent・スキル・認証・モデル・MCP・フック・グローバル指示は不変 |

上記はこの定義の受入れ条件であり、実アプリのアクセシビリティ認証やUX向上の実証ではありません。未実施の検査は未実施と報告します。
