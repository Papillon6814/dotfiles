# jig：小規模の実装を行うスキル

## 手順

### 1. 対象と完了条件を確認する

- 依頼、対象repo、現状、期待する結果、変更しない範囲を確認する。
- 対象コード、呼び出し元、関連テスト、適用される指示を実際に読む。記憶やIssueのcloseだけを根拠にしない。
- 不具合修正では **必須スキル：`superpowers:systematic-debugging`** を使い、再現と原因確認を先に行う。
- 完了条件を観測可能な形にする。例：「空入力では保存処理を呼ばず、既存のエラー表示を出す」。

### 2. 短い変更方針を承認してもらう

- 「何を変えるか」「対象ファイル」「何を変えないか」「どう検証するか」を短く提示する。
- 仕様変更や創作を伴う場合は **必須スキル：`superpowers:brainstorming`** を使う。
- 方針の明示承認後に編集する。既存資料の内容承認と、今回の実装開始許可は区別する。
- plan移行の閾値に該当したら移行を提案し、承認前に切り替えない。途中で影響が広がった場合も停止して相談する。

### 3. 最小限の実装を行う

- コード変更では **必須スキル：`superpowers:using-git-worktrees`** を使い、今回の作業用worktreeとfeature branchを確認する。作成には `git worktree add` を使う。
- 既存の未コミット変更を保護し、対象ファイルを読んでから編集する。無関係な整理や依存更新を混ぜない。
- コードの機能追加・修正では **必須スキル：`superpowers:test-driven-development`** を使い、変更対象を捉えるテストの失敗を確認してから最小実装する。
- 親による直接実装の可否、担当・委任・モデルの条件は共通規律に従う。小規模という理由で必須の役割を省かない。
- インストール、削除、上書き、外部投稿等は既存の確認条件に従う。本スキルは追加の操作権限を与えない。

### 4. 検証して結果を報告する

- **必須スキル：`superpowers:verification-before-completion`** を使い、対象テストと影響範囲に必要なtest/type-check/lintを実行する。
- 差分を読み、完了条件を満たすこと、対象外の変更や秘密情報の混入がないことを確認する。
- 共通規律で要求されるレビューは **必須スキル：`superpowers:requesting-code-review`** に従う。
- 未実施・失敗・確認不能はそのまま報告する。検証できていないものを完了としない。

## 最終報告

以下を短く記載する。

- 変更内容と対象ファイル。
- 完了条件に対する実際の結果。
- 検証コマンドと出力、未実施項目。
- 残作業・注意点。Git管理下の実装では対象branch/refも含める。

コミット・push・PR・merge・Issue更新は、それぞれ既存の操作許可に従う。実装の承認だけで公開や統合まで許可されたと扱わない。

## 避けること

- 「小さい変更だから」と、原因調査・方針承認・テストを省く。
- jigをscaffoldやProfileの承認・セッション分離を回避する入口にする。
- 調査中に見つけた別の問題を、無断で今回の変更に含める。
- テストが通ったことだけで、仕様や受け入れ条件の承認済みと判断する。
