# scaffold：要件定義から実装までを一気通貫で行うスキル

## 本スキルについて

- ユーザーからの要望に基づき、要件定義から実装までを一気通貫で行うスキル。
- 下記の表に基づいた工程を順番にたどり、要望の実現を目指す。

| 順番 | 工程             | 必須手順書                     | 説明                                               |
| ---- | ---------------- | ------------------------------ | -------------------------------------------------- |
| 1    | 環境セットアップ | `references/setup.md`          | 仕様策定前に、状況管理用の環境セットアップを行う。 |
| 2    | 仕様策定         | `references/specification.md`  | ユーザーヒアリングを行い、仕様を確定する。         |
| 3    | 基本設計         | `references/basic-design.md`   | 確定した仕様に基づき、システムの基本設計を行う。   |
| 4    | 詳細設計・実装   | `references/implementation.md` | 基本設計を基に、各機能の実装・検証を行う。         |
| 5    | 検証             | `references/tests.md`          | 完成したシステムの検証を行う。                     |

- 工程を進める際は同じ会話セッションで絶対に続けないこと。
- 人に質問してよいのは、環境セットアップ・仕様策定・基本設計の工程だけである。詳細設計・実装と検証の工程では、親も下位の担当も人に質問せず、下位の質問は親が捌く（Development の `instructions.md` の「質問と判断」。厳守）。例外は、人にしかできない事前作業が欠けて止まったときの `【事前作業】` の依頼だけである（同じ節）。
- 各工程が完了したことを確認してから、次の工程へと進む。

## 用語と開発順序

| 単位            | 役割                                         | 作成する段階   |
| --------------- | -------------------------------------------- | -------------- |
| `Epic Issue`    | 機能全体の仕様と完了条件を管理する親Issue    | 仕様策定       |
| `Feature Issue` | 基本設計に基づく、独立して完了できる成果単位 | 基本設計       |
| `Task Issue`    | Featureの詳細設計から切り出す実装・検証単位  | 詳細設計・実装 |

- 仕様策定、基本設計、詳細設計・実装の3つの会話セッションで進める。必ず別セッションとし、同一会話内のモード切替で代用しない。
- 詳細は各段階のreference内に記載するが、次の段階へ進む際はherdr経由で同一workspace内にタブを作り、そこで同一認証・同一Profileでpiのセッションを立ち上げ、続きを進めるコマンドを実行する。
- Featureごとにcoding-managerを1人配置する。配下Taskのcoder・testerを管理し、Taskごとのmanagerは置かない。
- 他用途のセッションで新機能の要望が出た場合、背景・要望・決定事項・未決事項を整理して新しい仕様策定セッションへ引き継ぐ。仕様策定セッション内では、その会話で仕様を固めてよい。

## 管理物について

- 仕様や進捗の管理については以下の通り。

### 仕様の管理

- 仕様の正本は`Epic Issue`とする。すべてのエージェントが`Epic Issue`さえ参照すれば、当該システムの仕様が理解できるようにするべき。
