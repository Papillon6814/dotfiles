# SNS企画のAI実現制約

Research専用。技術的にできる、規約上使える、本人環境で使える、継続採算が合う、を分ける。
**開始前に `references/checklist.md` と `assets/output-template.md` を全文読む。** パスはスキル所在が基準。
共通の調査・モデル・質問・承認規律を維持。評価と試験案まで。実装・生成・認証変更・課金・公開試験は別承認。

## 1．入力と範囲

企画前の制約整理／案の実現性評価／運用見直しを扱う。
①出口と②ディレクションがあれば読み、必要な品質・形式・頻度・媒体・地域・素材供給・予算・人の時間・既決事項を引き継ぐ。先に致命的制約を調べる単独利用もできる。
仕事が変わる不足は親がask_userで1問ずつ確認し、子は親へ返す。試験・権利確認を無償・工数外と勝手に扱わない。

## 2．評価

1. 「必要な品質と頻度を、許された方法・費用・人の時間で継続できるか」を重要な問いにする。
2. 調査→企画→本文→画像・動画・音声→合成→検品→公開→計測から必要工程を選ぶ。各工程の必要品質、入力、担当・人の作業、方法、証拠と不足を表にする。
3. 要件を **対応可能／条件付き／未確認／現条件では不可** で判定。技術・権利／規約・本人の利用条件・総費用／時間を別欄にする。APIの存在、販売者の性能説明、生成単価だけで可能判定しない。
4. 初期設定、試験、不採用・再生成、合成、検品・修正、保管・公開・計測・障害対応まで費用と時間を見積もる。既知の範囲と記号の未知値を分け、予算内という結論は実測条件に限定する。
5. 必須品質を保つ代替案と小規模試験を作る。各試験を「入力・条件→観測→合格／保留→失敗時の代替」で書く。母数・試験費・人の検品を明記し、試験を実行済みにしない。
6. 全体を **試行可能／条件を満たしてから試行／設計の見直しが必要** と理由で返す。未確認の重要条件は保留。実現性の判定は①の事業効果や②の読者価値の合否ではない。

## 3．出力と戻し先

`assets/output-template.md` の順で、要件別4状態、工程・総費用・人の作業、代替、試験・全体判定、未確認・出典を残す。JSONロジックツリーへ根拠を接続。
①へは制作費・頻度・人の作業が採算を変える条件、②へは表現・品質・素材の変更条件を返す。固定の販売先・媒体・予算を勝手に変更しない。形式や頻度の変更も提案と決定を分ける。
連携未実施は未実施。利用不能なツール・担当・証拠を補完した扱いにしない。
AI非開示、全自動、毎日投稿、特定生成モデルを初期値にしない。権利・規約・必要表示・利用資格が未確認なら、利用可能・公開可と判定しない。
